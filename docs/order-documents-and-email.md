# Order documents and confirmation emails

## Customer and seller flow

Checkout saves an order summary and one commercial invoice and packing slip per seller in the same transaction as inventory and the order. Each stores the order's prices, quantities, delivery fees, customer delivery address and seller identity at purchase time. PDFs use the bundled Yaans.lk logo, burgundy/gold header, structured address cards, repeated item-table headers, LKR totals and page numbers. Receipts/refunds have distinct payment labels. Long orders paginate without splitting rows, and the final item stays with the totals. Packing slips omit all financial columns. Local Latin, Sinhala and Tamil fonts preserve multilingual names and items without remote asset fetching. Commercial invoices are not labelled tax invoices. The platform summary is not a substitute for a seller's tax invoice.

Customers can view and download PDFs from checkout confirmation, order history and tracking. Guest access requires the existing unexpired capability in a request header. Sellers can access only their own packages. Administrators can access order documents from the order list. There are no public PDF URLs or shared caches. Documents and PDF code load only when requested; checkout does not render PDFs or await the email provider.

The original invoice remains unchanged after cancellation, collection or refund. Existing cash reconciliation creates a separate receipt when collection/remittance is recorded, and a refund confirmation only when a refund is recorded. Delivery by itself does not prove payment. Cancellation creates its own confirmation. Bank/courier internal references, commission and seller earnings do not appear in customer documents. Historical orders have clearly labelled copies based on saved order lines, with no fabricated historic seller address.

## Free-first email setup

The implementation uses Resend's transactional HTTP API. At implementation time its free plan offers 3,000 emails/month and 100/day; confirm current terms at https://resend.com/pricing before activation. No paid subscription is enabled by this change. A receiving inbox for customer replies is a separate service.

1. Create or use your Resend account on the Free plan. Add a sending domain such as `mail.yaans.lk` (or use an already verified domain). Add exactly the SPF/DKIM DNS records Resend provides, then wait for verified status. Do not replace unrelated mail records. Configure DMARC with your domain administrator.
2. Create a restricted sending API key and enter it directly in Vercel as production `RESEND_API_KEY`. Never put the key in source control or a chat.
3. Set `ORDER_EMAIL_FROM` to an address on the verified domain, for example `orders@mail.yaans.lk`. An existing `RESEND_EMAIL_DOMAIN` can supply the domain for the default `orders@...` sender. Set `DOCUMENT_BUSINESS_NAME` and `DOCUMENT_BUSINESS_ADDRESS` to the actual platform identity. Seller invoices use each seller's saved store name, business address and phone, never their private NIC/BR or bank details. Have the seller/accountant confirm the appropriate legal invoice identity and tax requirements before relying on these as formal tax documents.
4. Set production `ORDER_EMAIL_ENABLED=true` only after verifying sender configuration and arranging an authorized test recipient. Preview/staging environments are never allowed to send. Redeploy to apply changes.
5. Generate a random secret of at least 32 characters. Configure it as production `ORDER_EMAIL_WORKER_SECRET` in Vercel and the same named GitHub Actions secret. Set GitHub repository variable `ORDER_EMAIL_WORKER_ENABLED=true`. The included hourly workflow retries bounded batches on the default branch. It stays skipped until explicitly enabled. The worker POST URL is `https://yaans.lk/api/documents/email-worker`; an external scheduler can call it with `Authorization: Bearer <secret>` if faster recovery is needed. GitHub scheduled runs can be delayed; monitor queue age and your Actions allowance. Automatic sending happens immediately through Vercel's supported background lifetime extension; the hourly worker is a recovery path.
6. In the admin dashboard, open **Check email delivery status**. Configuration gaps are visible and queued jobs remain durable. **Process queued emails** runs a bounded retry batch. “Accepted by provider” does not prove inbox delivery; inspect delivery/bounce status in Resend. No bounce webhook is installed in this release.

## Reliability and limits

One outbox job is created per successful order, atomically with checkout. Checkout retries do not duplicate jobs. Guest tracking capabilities are encrypted with a domain-separated key derived from the existing JWT secret, then removed from the job after sending. Keys never appear in public URLs to the API, job status endpoints or logs; the email tracking link carries the code in its fragment. JWT rotation also invalidates pending encrypted capabilities, which then require operator review.

Workers use an indexed atomic lease, bounded batches, an eight-second provider timeout and exponential retries. The provider's idempotency key is stable for each order; retries retain identical sender and body. Unsent confirmations older than 20 hours require review, so stale queues or restored backups cannot automatically replay old confirmations. Automatic retries also stop within 20 hours of the first attempt (inside Resend's 24-hour key window) or after six attempts. Ambiguous/expired attempts and permanent provider errors require review rather than risking a duplicate. Do not reset an ambiguous job without checking provider records.

Conservative application budgets reserve at most 95 logical emails/day and 2,900/month. Reservations use MongoDB transactions and do not repeat on retries. These budgets do not account for email sent by other applications using the same account; provider limits still apply. Pending jobs wait when a budget is exhausted. Upgrading Resend does not automatically increase these application budgets; adjust them deliberately with tests when growth requires it.

Production activation and live email delivery require the verified sender, provider key, worker secret and a permitted recipient. Automated tests use isolated MongoDB and mocked provider responses; they never send real customer emails.
